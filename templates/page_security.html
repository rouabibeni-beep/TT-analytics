🔒 Sécurité & algorithmes d'analyse

Guide pour l'analyste : comment les logs JBoss/WildFly deviennent des alertes, comment interpréter les scores et quelles actions mener à chaque niveau.

Chaque journée est découpée en 288 fenêtres de 5 minutes. Le modèle compare chaque fenêtre au comportement « normal » observé sur la même période. En cas d'alerte, SHAP indique quels signaux ont le plus contribué au score.

Étape 1 — Parsing des logs (parse_logs.py)

Objectif : transformer des fichiers logs bruts (souvent compressés .gz) en une table structurée exploitable par le machine learning.

Ce que fait l'algorithme :

  • Lit chaque ligne avec une expression régulière : horodatage, niveau (INFO, WARN, ERROR…), composant, thread, message.
  • Extrait les codes d'erreur connus : ARJUNA (transactions XA), IJ (pool de connexions), JBAS, etc.
  • Classifie le composant : gestionnaire de transactions, pool, couche web, SSH, application métier…
  • Marque les événements sensibles : authentification, accès refusé, timeout, stack trace, exception Java.
  • Assigne chaque événement à une fenêtre de 5 minutes (time_window).

Sorties : logs_parsed.csv · rapport parsing_summary.txt (taux de lignes non parsées, volume par niveau).

Pour l'analyste : si le taux de parsing est bas, les anomalies peuvent être sous-estimées — vérifier le format des logs avant d'interpréter le dashboard.

Étape 2 — Feature engineering (features.py)

Objectif : résumer l'activité de chaque fenêtre de 5 min en indicateurs numériques comparables dans le temps.

Principales familles de features :

  • Volume : total_events, nb_error, nb_warn, ratios erreur/avertissement.
  • Sévérité : severity_mean, severity_max (pondération DEBUG→FATAL).
  • Composants : événements transaction manager, pool connexion, web, SSH, appli télécom.
  • Codes métier : nb_arjuna, nb_ij, nb_jbas — ciblage rapide du sous-système en panne.
  • Signaux critiques : nb_security, nb_timeout, nb_stacktrace, nb_exception.
  • Contexte temporel : z-scores sur 1 h glissante (pic soudain vs tendance) · deviation_vs_hour_baseline (pic inhabituel à cette heure de la journée).

Sorties : features.csv (une ligne par fenêtre) · features_report.txt (top fenêtres suspectes en règles heuristiques).

Pour l'analyste : une fenêtre anormale n'est pas qu'un « pic d'erreurs » — regarder aussi la sécurité, les timeouts et le composant dominant.

Étape 3 — Isolation Forest (model.py)

Objectif : détecter automatiquement les fenêtres atypiques sans étiquettes manuelles (apprentissage non supervisé).

Principe : l'algorithme construit des arbres qui isolent aléatoirement les points. Une fenêtre très différente des autres est isolée en peu de coupes → score d'anomalie élevé.

Paramètres du projet :

  • 200 arbres (n_estimators=200) pour stabiliser le score.
  • 15 % de contamination attendue — le modèle suppose qu'environ 15 % des fenêtres peuvent être atypiques sur la journée analysée.
  • 29 features ML normalisées (StandardScaler) : volume, ratios, composants, z-scores, écart à la baseline horaire.

Transformation du score : le score brut du modèle est converti en 0 à 100 (100 = le plus anormal de la journée). Ce score alimente le dashboard et la heatmap.

Sorties : resultats_modele.csv · model_report.txt · graphiques timeline / PCA / heatmap.

Pour l'analyste : un score élevé signifie « comportement rare sur cette journée », pas forcément une panne confirmée — toujours croiser avec les logs bruts de la fenêtre.

Étape 4 — SHAP — explicabilité (shap_xai.py)

Objectif : répondre à la question « Pourquoi cette fenêtre est-elle flaggée ? » après la détection automatique.

Principe : SHAP (SHapley Additive exPlanations) attribue à chaque feature une contribution au score. Les features avec la plus forte contribution positive expliquent l'alerte.

Exemples d'interprétation :

  • Score critique + forte contribution de nb_stacktrace → erreur applicative / exception non gérée.
  • Forte contribution de nb_security ou nb_security_zscore → pic d'événements auth / accès / credential.
  • Forte contribution de nb_ij ou nb_pool_ev → saturation ou fuite du pool de connexions.
  • Forte contribution de nb_arjuna → problème de transactions distribuées (XA).
  • Forte contribution de deviation_vs_hour_baseline → activité anormale pour l'heure (ex. pic à 3h du matin).

Sorties : shap_report.txt · graphiques d'importance globale, beeswarm et focus sur les anomalies critiques.

Pour l'analyste : utiliser SHAP pour prioriser la root cause avant d'ouvrir des centaines de lignes de logs — puis valider dans logs_parsed.csv sur la fenêtre concernée.

Étape 5 — Alertes & rapport (dashboard + PDF)

Objectif : centraliser les résultats pour le suivi opérationnel et la communication.

  • Page Base de données : KPIs, heatmap 24h, timeline score/erreurs, tableau des anomalies prioritaires.
  • Page Graphiques : distribution des sévérités, histogramme des scores, features SHAP.
  • Page Interprétation XAI : scénarios de lecture SHAP, bénéfices et feuille de route.
  • Rapport PDF : synthèse exportable pour comité ou escalade.

Pour l'analyste : traiter d'abord les fenêtres CRITIQUE, puis consulter SHAP, puis les logs sources sur l'intervalle horaire exact (ex. 14:30–14:35).

Seuils de score et conduite à tenir

ScoreNiveauSignificationAction analyste
0 – 45 NORMAL Comportement dans la norme de la journée Aucune action — surveillance passive
45 – 65 SUSPECT Légère déviation, possible bruit ou début d'incident Surveiller la tendance sur les 2–3 fenêtres suivantes
65 – 80 ANORMAL Comportement clairement atypique Ouvrir les logs de la fenêtre · identifier composant et code erreur
80 – 100 CRITIQUE Fenêtre parmi les plus anormales de la journée Intervention immédiate · SHAP · escalade si impact métier

Méthode d'investigation recommandée

  1. Repérer une alerte sur la heatmap ou le tableau des anomalies prioritaires.
  2. Noter l'heure exacte de la fenêtre (ex. 14:35 = fenêtre 14:35–14:40).
  3. Consulter le rapport SHAP pour les 3 features les plus contributives.
  4. Filtrer logs_parsed.csv sur cette fenêtre et ces types d'événements.
  5. Classer l'incident : applicatif, infrastructure, sécurité ou charge normale (batch).
  6. Documenter et exporter le rapport PDF si escalade nécessaire.
